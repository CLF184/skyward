Skyward 0.1.7 for the Xiaomi 15 Pro (`haotian`), made on the stock recovery
`OS4.0.0.19.XOBCNXM`.

Image: `skyward-v0.1.7-haotian-OS4.0.0.19.XOBCNXM.img`. Check it against
`SHA256SUMS`, then, with the phone in fastboot mode on the slot it runs from:

```sh
sha256sum --check SHA256SUMS
fastboot flash recovery skyward-v0.1.7-haotian-OS4.0.0.19.XOBCNXM.img
fastboot reboot recovery
```

## 这次修的内容

- **解不开的用户能解开了**。有些人的 data 分区只能通过 weaver（安全芯片里的
  槽位）解，而 weaver 又只能经安全元件访问；这条链上有三处没接上，现已补齐：
  - 安全元件 HAL 需要的 `ssgtzd`（TEE 的 mink 服务）从来没有启动过，所以它的
    `TEEC_OpenSession` 一律返回 `0xFFFF0000`：安全元件根本没打开，weaver 每次
    调用都只能报自己的 error 1。现在按手机自己的 init 起它，带两个监听 socket。
  - eSE 的内核驱动 `stm_st54se_gpio`、`stm_nfc_i2c` 没有加载，`/dev/st54spi_gpio`
    不存在，HAL 报 `eseGetVendorId: Unknown eSE HW`。现在启动时一并加载。
  - 安全元件 HAL 改回以 root 运行，并等 ADSP 就绪后再起服务。
- **ADSP 起不来时不再干等**。DSP 的固件在 `/vendor/firmware` 里可能只有前半段
  （缺 `adsp.b28` 这类分段），内核读到就停，DSP 全程 offline。原来会白等 60 秒
  才亮屏。现在只等 3 秒；仍是 offline 就请求加载器重试一次（`/firmware` 此时已
  就位，而它在内核搜索路径的最后），再等 10 秒。运行中的 DSP 绝不写这个开关，
  也绝不写 `ssr`。
- **双击亮屏**。息屏后双击面板即可点亮，和手机自己的系统一致（300 ms 内、两次
  落点相距不超过屏宽的 8%）。代价是开了双击的机型在息屏时不再进入 suspend——
  睡下去就收不到触摸了。
- 打包工具不再依赖外部 `lz4` 程序，改用 Rust 直接写 legacy 帧；设备配置里的路径
  校验在 Windows 上也能过（`has_root` 而非 `is_absolute`）。

## 怎么确认装上了

`adb shell dmesg | grep -i "the ADSP"`：

```
skyward: /sys/class/remoteproc/remoteproc1 runs, so the secure element's HAL can reach it
```

解锁之后，有 weaver 的用户应当不再出现

```
the users whose own files are still closed: [0]
```

如果 DSP 一直起不来，会看到 `the ADSP is offline; asked the loader again now that
/firmware is in place`，随后跟 `it is not running, even after the loader was asked
again` —— 把这行发出来即可定位。

## This release in English

Three links in the chain that decrypts a user whose secret is bound to the
weaver were missing, and all three are now in place: the TEE's mink daemon
`ssgtzd` is started with the two listeners the phone's own init gives it
(without it the secure element's `TEEC_OpenSession` fails with `0xFFFF0000`,
so the element never opens and every call to the weaver answered with its own
error 1); the eSE's kernel drivers `stm_st54se_gpio` and `stm_nfc_i2c` are
loaded, so `/dev/st54spi_gpio` exists; and the secure element's HAL runs as
root, after the ADSP is up.

The wait for the ADSP is three seconds rather than sixty, and a DSP that could
not start is asked for again once `/firmware` is in place — where the kernel's
own firmware search ends — because the rest of its firmware is on the modem
partition and nothing has to be copied for it. The double tap that lights the
dark panel is here too, as the phone's own system has it.
